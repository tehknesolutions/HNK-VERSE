## 1. Purpose

The Mandala-HNK Computational Model (MHCM) defines the structural interface between the Mandala-HNK research model and the computational HNK-KODE pipeline.

MHCM is not itself a programming language, compiler, runtime, or canonization mechanism.

Its first purpose is to define contracts for Cell, Address, Edge, Path, Glyph, Transform, Composition, Type, Operator, and Program.

Immediate target:

Mandala / structural representation ↔ HNK-KODE AST ↔ HNK-IR

## 2. Authority and status

- CODEX-HNK = canonical authority for HNK definitions and approved contracts.
- HNK-KODE = language and computational authoring layer.
- MHCM = computational model/specification for Mandala-related structures.
- HNK-VERSE = runtime/manifestation consumer.
- TKN-OS = institutional memory/lineage system of Tehkné Solutions.

## 3. Relationship to HNK-KODE

The existing HNK-KODE programming-language baseline defines:

HNK-KODE → Lexer / Parser → AST → Semantic Analyzer / Type Checker → HNK-IR → target → HNK-VERSE Runtime

MHCM can participate as:

HNK-KODE → AST → MHCM projection → HNK-IR → Runtime

or, as a future capability:

Mandala representation → MHCM → AST → HNK-IR → Runtime

The second path is not yet implemented.

## 4. Core model

### Cell

A Cell is the smallest addressable structural unit recognized by MHCM.

A Cell has a stable identifier, coordinate/address, optional layer, optional sector, optional semantic classification, provenance, and schema version.

A Cell does not acquire semantic meaning merely because it exists geometrically.

### Address

An Address identifies a Cell or other MHCM object.

Conceptual form:

Address = namespace + coordinate + version

The exact serialization is intentionally unfrozen.

An Address must be deterministic, serializable, comparable, version-aware, and provenance-preserving.

### Edge

An Edge represents an allowed structural relation between two addressable nodes.

Conceptual form:

Edge = source + target + relation + optional direction

Direction must be explicit whenever direction is semantically relevant.

### Path

A Path is an ordered traversal of nodes and edges.

Conceptual form:

Path = start + node_sequence + edge_sequence + end

A Path may be directed, undirected, reversible, constrained, or typed.

Whether two Paths are equivalent is determined by an explicit equivalence relation, not visual intuition.

### Glyph

A Glyph is a structured representation generated from an MHCM construction.

Conceptual form:

Glyph = anchor + path + transform + encoding

A Glyph is not required to be a phoneme, letter, word, or programming opcode.

Its linguistic or computational meaning must come from an explicit higher-level contract.

### Transform

A Transform maps one valid structural representation to another.

Possible classes include rotation, reflection, reversal, translation, projection, and normalization.

The allowed transform set is versioned.

### Composition

Composition combines valid MHCM objects.

Composition(A, B) → C

Composition rules must state input types, output type, ordering, associativity where applicable, reversibility where applicable, and provenance behavior.

### Type

Initial conceptual types are Cell, Address, Edge, Path, Glyph, Transform, Composition, Operator, and Program.

No type receives language semantics solely from its name.

### Operator

An Operator is an explicit transformation or computation over typed MHCM values.

Operator<T1...Tn> → T

Operators must be versioned and type-checked.

### Program

A Program is an ordered, typed composition of declarations and operations that can be projected into AST/HNK-IR.

A Program is executable only after passing HNK-KODE compiler and runtime contracts.

## 5. Mandala dimensions under investigation

Historical HNK-KODE research contains:

- 72 sectors × 6 layers = 432 MF cells;
- 463 active/addressable fields;
- 504 physical raster positions;
- 41 reserved positions.

These figures are recorded here as RESEARCH/STRUCTURAL HYPOTHESES unless separately promoted by CODEX-HNK authority.

Therefore:

432 != automatically 432 opcodes
463 != automatically 463 language units
504 != automatically 504 syntax positions

MHCM must remain valid even if these figures are revised.

## 6. HNK40 relationship

HNK40 is treated as a historical/experimental corpus and validation dataset.

It is not assumed to be the final HNK-KODE alphabet, final number of programming primitives, final glyph inventory, or complete language vocabulary.

Promotion requires explicit authority.

## 7. E5 and combinatorial space

Previous E5 work produced a raw structural walk count for N=12:

7,289,096,672

This is not the number of unique glyphs or words.

MHCM therefore separates:

1. Raw structural space
2. Structurally valid space
3. Equivalence-reduced space
4. Visually distinct space
5. Linguistically usable space
6. Computationally usable space

No layer may silently substitute for another.

## 8. Equivalence

Equivalence is a first-class concept.

Future specifications must define independent equivalence relations for exact identity, path identity, reversal, rotation, reflection, normalized geometry, visual identity, linguistic identity, and computational identity.

Two representations may be visually equivalent while remaining distinct addresses.

Two distinct visual representations may map to the same computational value only through an explicit rule.

## 9. Provenance

Every generated MHCM object should be traceable to source dataset, generator/version, schema version, input objects, transforms, validation result, and authority state.

Minimum conceptual lifecycle:

RAW → OBSERVED → EXPERIMENTAL → REVIEWED → APPROVED → CANON

Parallel states may include REJECTED, SUPERSEDED, DEPRECATED, and ARCHIVED.

MHCM generation must never silently change provenance.

## 10. Mapping to HNK-KODE AST

The first intended mapping is structural rather than semantic.

Cell → address literal / structural node
Path → path expression
Transform → transform expression
Composition → composition expression
Operator → operator expression
Program → program/module node

Exact AST node names are deferred to the KODE grammar spike.

MHCM must not force a grammar before parser/type-system validation.

## 11. Mapping to HNK-IR

HNK-IR must remain independent of textual syntax.

A future IR representation should preserve at least object identity, type, source/provenance reference, structural references, operation, operands, expected output type, and schema version.

Conceptual form:

IRNode = { id, type, op?, inputs[], metadata, provenance }

This is illustrative, not a frozen serialization schema.

## 12. Validation requirements

The MHCM validator must eventually verify:

- address validity;
- edge validity;
- path validity;
- type compatibility;
- transform validity;
- composition validity;
- deterministic serialization;
- round-trip conversion;
- provenance integrity;
- uniqueness where required;
- schema/version compatibility.

Validator states:

PASS
FAIL
AMBIGUOUS
UNSUPPORTED

AMBIGUOUS must not be silently promoted to PASS.

## 13. Round-trip requirement

Where a representation claims reversibility, MHCM must test:

A → B → A

Potential future round trips include:

TEXT → AST → IR → AST → TEXT

and:

MANDALA → MHCM → AST → MHCM → MANDALA

Lossy transformations must be explicitly marked as lossy.

## 14. Computational grammar hypothesis

MHCM permits investigation of a future model in which:

- position can provide address/context;
- PATH can provide structural expression;
- composition can provide grouping;
- transform can provide modifiers;
- operators can provide computation;
- types can provide semantic constraints.

This is a hypothesis to test, not a declaration that the Mandala already is a programming grammar.

## 15. Minimal proof

The first proof-of-concept should be deliberately small:

1. Define a minimal Cell set.
2. Define valid Edges.
3. Construct one Path.
4. Encode the Path as a Glyph/structural object.
5. Map it into an AST node.
6. Lower it into HNK-IR.
7. Validate the IR.
8. Execute one harmless deterministic runtime action.

The proof succeeds only if the entire chain is reproducible.

## 16. KODE-0 integration

MHCM must not block the minimal HNK-KODE grammar spike.

KODE-0 remains:

world → entity → property → event → action

The first implementation may use ordinary textual syntax and ordinary AST nodes.

MHCM integration should be introduced as a validated projection after the basic compiler loop works.

## 17. Non-goals

MHCM v0.1 does not define:

- final HNK-KODE grammar;
- final HENUVOKODAN grammar;
- final glyph inventory;
- final Mandala semantics;
- final opcode table;
- a virtual machine;
- a native compiler;
- a visual IDE;
- automatic canonization;
- a claim that 432/463/504 are final language cardinalities.

## 18. Next implementation gates

### MHCM-1 — Data model

Implement typed interfaces/schemas for Cell, Address, Edge, and Path.

### MHCM-2 — Validator

Implement deterministic validation for topology and typing.

### MHCM-3 — Serialization

Define canonical JSON representation and round-trip tests.

### MHCM-4 — Glyph projection

Represent a Path as a deterministic structural Glyph object.

### MHCM-5 — AST bridge

Map one validated MHCM construction into a KODE AST node.

### MHCM-6 — HNK-IR bridge

Lower the AST node into stable HNK-IR.

### MHCM-7 — Runtime proof

Execute one deterministic, side-effect-limited manifestation in HNK-VERSE.

## 19. Definition of done

MHCM v0.1 is operational when:

- Cell/Address/Edge/Path schemas exist;
- invalid topology is rejected;
- valid paths serialize deterministically;
- round-trip tests pass;
- provenance survives transformations;
- at least one Glyph projection is reproducible;
- at least one MHCM object reaches AST;
- at least one AST node reaches HNK-IR;
- CI proves the chain without requiring a local machine.

## 20. Strategic position

MHCM is the bridge between the research geometry of Mandala-HNK and the executable architecture of HNK-KODE.

The correct progression is:

RESEARCH → FORMALIZATION → VALIDATION → IMPLEMENTATION → PROMOTION

not:

RESEARCH → ASSUMPTION → CANON

The immediate objective is not to prove that every Mandala property has computational meaning.

The objective is to build a falsifiable, versioned interface through which computational meaning can be tested.
