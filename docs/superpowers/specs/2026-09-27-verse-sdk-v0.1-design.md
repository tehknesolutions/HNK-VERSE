# HNK-VERSE — Verse SDK v0.1 Design Specification

Status: WRITTEN SPEC — AWAITING USER REVIEW
Date: 2026-09-27
Parent product proof: `docs/product/2026-09-27-hnk-verse-zero-vertical-slice-v1.md`

## 1. Intent

Verse SDK v0.1 is the contract surface through which an independently governed Verse or Experience participates in HNK-VERSE.

It exists to let heterogeneous realities interoperate without turning HNK-VERSE into one monolithic game engine and without forcing Verses to share gameplay semantics.

Approved architectural principles:

1. **Contract-first + runtime-agnostic.**
2. **Minimal Core + optional modules.**
3. **Platform-controlled boundary + Verse-controlled interior.**

Canonical shorthand:

`PLATFORM OWNS THE BORDER → VERSE OWNS ITS REALITY → CONTRACT GOVERNS THE CONNECTION`

## 2. Non-goals

Verse SDK Core is not:
- a game engine;
- a renderer;
- a physics engine;
- a universal combat/inventory/quest system;
- HNK-KODE itself;
- CODEX-HNK;
- a universal economy;
- an asset editor;
- a mandate that all Verses use the same implementation language.

## 3. Architecture

`HNK-VERSE Protocol Contracts → Verse SDK Core → Runtime Adapter → Verse/Experience`

The protocol contracts are the authority. Runtime adapters provide language/engine ergonomics without changing contract semantics.

Initial adapter direction:
- TypeScript/Web adapter first;
- future engine/runtime adapters;
- future HNK-KODE adapter/runtime binding.

HNK-KODE remains a sibling/transversal project and does not live inside Verse SDK.

## 4. Core surface

Verse SDK Core v0.1 contains seven contract families.

### 4.1 Context

Provides the authorized runtime view required by a Verse operation.

Conceptual fields/refs:
- platform identity ref;
- session ref;
- presence ref;
- Verse/context ref;
- embodiment ref where applicable;
- granted roles/permissions;
- correlation/trace ref;
- contract versions.

Context is capability-bounded. It does not expose authentication secrets.

### 4.2 World

Provides stable references and bounded operations for:
- HNK-ID/entity refs;
- HNK-Address/location refs;
- Space/world node refs;
- typed relations;
- entity resolution;
- allowed entity/world mutations.

The SDK preserves `HNK-ID != HNK-Address` and the typed-graph World Model.

### 4.3 Capabilities

Provides:
- Verse Capability Manifest retrieval/validation;
- platform compatibility checks;
- capability negotiation;
- permission/policy evaluation hooks;
- explicit unsupported results.

Invariant:

`ABSENT CAPABILITY = UNSUPPORTED BY DEFAULT`

### 4.4 Transition

Provides cross-context lifecycle for:
- enter;
- exit;
- return;
- portal travel;
- embodiment resolution;
- presence transition;
- failure/compensation results.

A transition is not a raw teleport call. It is a negotiated boundary operation.

### 4.5 Interop

Provides typed cross-boundary outcomes:
- `REJECT`;
- `REFERENCE`;
- `PROJECT`;
- `TRANSLATE`;
- `TRANSFER`;
- `CLONE`.

Every operation preserves authority and provenance. Translation does not assert semantic identity; projection does not transfer ownership.

### 4.6 Chronicle

Provides authorized event interaction:
- emit permitted events;
- attach causation/correlation;
- query/subscribe to permitted streams or projections;
- preserve event authority and schema versions.

The SDK distinguishes command/intent from committed Event.

`RUNTIME EVENT != CODEX-HNK CANON`

### 4.7 Lifecycle

Minimum Verse lifecycle:

`initialize → ready → enter → active → suspend/resume → exit → dispose`

Lifecycle hooks receive bounded Context and explicit results/errors. A Verse may have internal lifecycle states beyond this contract.

## 5. Optional modules

Modules extend the Core without making their capabilities universal.

Initial module directions:
- `creator` — artifacts, validation, sandbox, publishing hooks;
- `social` — platform/Verse social integration;
- `simulation` — standardized integration surfaces where useful;
- `assets` — asset refs/import/compatibility contracts;
- `economy` — future governed economic interfaces;
- future modules based on demonstrated platform needs.

A Verse remains valid without optional modules unless its own manifest declares a dependency.

## 6. Boundary ownership

### Platform owns the border

HNK-VERSE controls or authoritatively evaluates:
- platform identity resolution;
- authentication/session boundary;
- platform authorization;
- capability negotiation;
- entry/exit contract;
- cross-Verse transfer/projection/translation policy;
- platform provenance/correlation;
- platform Chronicle authority;
- platform security constraints.

### Verse owns its reality

Within granted boundaries, the Verse controls:
- gameplay;
- simulation;
- Verse progression;
- Verse inventory/economy;
- narrative state;
- local entities/systems;
- rendering/presentation;
- internal AI/game logic;
- Verse-local Chronicle event classes under declared authority.

### Contract governs connection

Neither side silently assumes semantics owned by the other.

## 7. Runtime adapter contract

A Runtime Adapter maps native runtime/language ergonomics to protocol contracts.

An adapter may provide:
- typed client/server bindings;
- serialization/deserialization;
- schema validation;
- transport abstraction;
- lifecycle integration;
- error mapping;
- developer ergonomics.

An adapter may not:
- redefine capability semantics;
- bypass permissions;
- manufacture event authority;
- silently convert unsupported state;
- promote runtime state into CODEX-HNK canon.

## 8. Versioning

Every contract family is independently versioned where practical.

Conceptual compatibility examples:
- `world: 2.x`;
- `identity: 1.x`;
- `capabilities: 1.x`;
- `chronicle: 1.x`;
- `verse-sdk: 0.1`.

Exact package/version syntax is an implementation-plan decision.

Rules:
- breaking semantic changes require a new incompatible contract version;
- additive optional fields/capabilities must follow declared compatibility rules;
- manifests declare required/supported ranges;
- no silent downgrade;
- fallback behavior must be explicit.

## 9. Error model

Errors/results are typed and boundary-aware.

Minimum families:
- `UNSUPPORTED_CAPABILITY`;
- `INCOMPATIBLE_VERSION`;
- `PERMISSION_DENIED`;
- `INVALID_CONTEXT`;
- `IDENTITY_RESOLUTION_FAILED`;
- `ENTITY_NOT_FOUND`;
- `INVALID_ADDRESS`;
- `TRANSITION_REJECTED`;
- `TRANSFER_REJECTED`;
- `TRANSLATION_FAILED`;
- `PROJECTION_FAILED`;
- `VERSE_UNAVAILABLE`;
- `VALIDATION_FAILED`;
- `CONFLICT`;
- `TIMEOUT`;
- `INTERNAL_VERSE_ERROR`;
- `PLATFORM_BOUNDARY_ERROR`.

Expected policy rejections are results, not necessarily exceptional crashes.

Errors carry safe correlation/diagnostic refs without leaking secrets.

## 10. Negotiation protocol

Canonical sequence:

`REQUEST → RESOLVE CONTEXT → LOAD MANIFEST → VERSION CHECK → CAPABILITY CHECK → PERMISSION CHECK → POLICY CHECK → NEGOTIATE → EXECUTE/REJECT → CHRONICLE`

Negotiation output is explicit and typed.

A client must never infer acceptance from absence of an error response.

## 11. Transition protocol

Conceptual transition state machine:

`REQUESTED → RESOLVING → NEGOTIATING → PREPARING → EXITING_SOURCE → ENTERING_TARGET → COMPLETED`

Failure states may occur at every boundary and produce explicit result/compensation behavior.

Required transition data includes:
- source context;
- target context;
- identity;
- requested interop set;
- manifest/contract versions;
- correlation ID;
- resulting embodiment/presence refs;
- interop outcomes;
- provenance refs.

## 12. Hub → Alakazam example

1. Hub requests entry to Alakazam.
2. Platform resolves identity/session/presence.
3. Alakazam manifest is loaded.
4. Compatible contract versions are confirmed.
5. Alakazam declares Verse-native embodiment.
6. External gameplay inventory transfer is unsupported/rejected.
7. Platform identity remains stable.
8. Existing Alakazam embodiment/state is loaded or created according to Alakazam policy.
9. Hub presence exits; Alakazam presence enters.
10. Chronicle records the correlated causal chain.
11. Inside Alakazam, Alakazam owns gameplay reality.

No Hub or HNK-Alchemy mechanic becomes Alakazam state by implication.

## 13. Hub → HNK-Alchemy example

1. Hub requests entry to HNK-Alchemy.
2. Identity/context resolves.
3. HNK-Alchemy manifest declares its embodiment/presentation policy.
4. A declared cosmetic/symbolic artifact is eligible for `PROJECT` or `TRANSLATE`.
5. The mapper/projection policy is versioned and authorized.
6. Result receives target refs and provenance to source.
7. HNK-Alchemy local state remains isolated.
8. Chronicle records projection/translation and transition.
9. Returning to Hub destroys/expires contextual projections according to policy without destroying source identity/artifact.

## 14. Creator module boundary

Creator/Publishing is not mandatory Core.

The optional Creator module builds on Core Context, World, Capabilities and Chronicle and exposes:
- Creator Artifact refs;
- draft/revision operations;
- validation hooks;
- sandbox/preview hooks;
- publish/version lifecycle;
- dependency/capability diagnostics.

This prevents a Verse that only wants to host a fixed experience from carrying editor semantics.

## 15. Security model

The SDK follows least authority.

A Verse receives only the platform capabilities and context required for the current operation.

Core invariants:
- authentication secrets are not world data;
- capability existence does not grant permission;
- identity continuity does not preserve permissions automatically;
- delegated agents retain attribution;
- external scripts do not gain unrestricted host access;
- cross-Verse writes require explicit ownership/policy authority.

## 16. Transport neutrality

Protocol contracts must not require one transport.

Potential bindings may use in-process calls, HTTP, WebSocket, worker/process messages or future transports.

Transport selection belongs to adapters/deployment architecture, while observable contract semantics remain stable.

## 17. Serialization neutrality

Core semantics are serialization-independent.

The first implementation may use JSON-compatible schemas for TypeScript/Web practicality, but contract definitions must distinguish semantic model from wire representation.

Future HNK-KODE/Mandala encodings may map to the same semantics through versioned adapters.

## 18. HNK-KODE integration

Future relationship:

`HNK-KODE SOURCE → HNK-KODE TOOLCHAIN → VALIDATED ARTIFACT → HNK-KODE RUNTIME ADAPTER → VERSE SDK CONTRACTS → HNK-VERSE`

HNK-KODE may author worlds, systems, UI, services or Verse behavior, but cannot bypass SDK boundary rules.

Verse SDK does not own HNK-KODE grammar/compiler specification.

## 19. HNK-Math / Mandala boundary

The SDK supports opaque/versioned HNK-ID, address/signature and structured metadata fields required by HNK-Math/Mandala evolution.

v0.1 must not invent mathematical semantics that CODEX-HNK/HNK-KODE have not frozen.

Adapters may expose typed wrappers once those contracts are authoritative.

## 20. ZERO-required SDK subset

Only the following must be implemented for ZERO:

- Context resolution;
- stable entity/world refs;
- three Capability Manifests (Hub/A/B);
- compatibility/capability negotiation;
- portal enter/return transition;
- Verse-native embodiment resolution for A;
- one rejected external gameplay state;
- one projection/translation path for B;
- Chronicle event envelope with causation/correlation;
- lifecycle hooks for Hub/A/B;
- Creator module subset required for Personal Space object publish flow.

Everything else is extension space, not v0.1 implementation debt.

## 21. Contract conformance tests

The SDK must eventually ship implementation-independent conformance fixtures/tests.

Minimum v0.1 scenarios:
1. undeclared capability is rejected;
2. incompatible contract version is rejected;
3. permission denial differs from unsupported capability;
4. identity remains stable across transition;
5. Verse A state remains isolated;
6. rejected transfer does not block separately accepted projection when policy allows;
7. projection retains provenance;
8. Chronicle correlation/causation survives adapter boundary;
9. Verse failure cannot forge `TransitionCompleted`;
10. adapter cannot bypass Core policy semantics;
11. published Creator version remains immutable after draft edits.

These fixtures become the basis for TypeScript and future HNK-KODE adapter compatibility.

## 22. Package/module direction

Conceptual package topology only; final names are decided in implementation planning:

- `contracts/core`
- `contracts/world`
- `contracts/capabilities`
- `contracts/transition`
- `contracts/interop`
- `contracts/chronicle`
- `sdk/core`
- `sdk/modules/creator`
- `adapters/typescript`
- future `adapters/hnk-kode`

The architecture favors explicit dependencies and small packages over a monolithic SDK bundle.

## 23. Acceptance criteria for SDK v0.1 design

The design is successful if:
- a Verse can integrate without adopting another Verse's gameplay model;
- HNK-VERSE can authoritatively govern entry/exit and interoperability;
- TypeScript can implement the contracts without becoming the contract definition itself;
- HNK-KODE can later target the same semantics;
- ZERO can be built without inventing new universal systems;
- optional Creator behavior does not pollute fixed-content Verses;
- every cross-boundary operation remains explicit, versioned, authorized and traceable.

## 24. Decisions intentionally deferred

Implementation planning will decide:
- exact TypeScript package names;
- schema technology/library;
- transport used by ZERO;
- monorepo package layout details;
- generated-code strategy;
- concrete persistence technology;
- exact wire serialization;
- exact HNK-ID encoding;
- final HNK-Math/Mandala encoding;
- HNK-KODE compiler/runtime implementation.

These are not required to validate the SDK architecture.

## 25. Architecture summary

Verse SDK v0.1 is a small, contract-first interoperability layer for a heterogeneous metaverse.

It gives HNK-VERSE authority over boundaries while preserving Verse autonomy inside those boundaries.

It deliberately universalizes only what ZERO proves must be universal.

**Platform owns the border. Verse owns its reality. Contract governs the connection.**
